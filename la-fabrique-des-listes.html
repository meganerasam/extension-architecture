La fabrique des listes

Tout ce qui entre, tout ce qui est filtré, tout ce qui sort — avec les vrais noms des onglets, les vrais fichiers et les comptes du run courant. Cinq étages : les miroirs, la curation, la vérification DNS, l'assemblage, et le catalogue à la carte.

block — bloque des requêtes redirect — intercepte une navigation allow — re-autorise / whitelist veto — retire, ne produit jamais de règle data — servi tel quel, jamais mergé

01 · La grande carte

Qui fait quoi, du haut vers le bas

La carte en clair — étage par étage, sans jargon :

Les sources (en haut) : tout ce qui entre. Tes Google Sheets — les listes que tu tiens à la main —, des listes publiques reconnues (la famille EasyList et quatre fichiers « hosts »), et les votes « Autoriser » remontés par les utilisateurs des extensions.

0 · Ingest : le robot photocopie chaque source telle quelle, plusieurs fois par jour. Si une source répond bizarrement, on garde la photocopie précédente et le run passe au rouge — une donnée douteuse n'entre jamais dans la chaîne.

1 · Curate : le tri. On construit d'abord la liste des domaines à ne jamais bloquer (tes vetos + les sites massivement autorisés par les utilisateurs), puis on la soustrait de chaque source — chacune selon sa propre recette, et chaque retrait est tracé dans un rapport.

2 · Verify : chaque domaine candidat est testé régulièrement — existe-t-il encore ? Un domaine mort n'est jamais publié.

3 · Compile : l'assemblage. Toutes les listes triées deviennent un seul fichier de règles pour Chrome, avec des plafonds chiffrés et des vérifications qui bloquent la publication au moindre doute.

4 · Catalog : la même matière, rangée à la carte — chaque source séparément, en version brute et en version triée, plus les cumuls — pour prendre exactement ce dont on a besoin.

Les 6 marques (en bas) : les extensions ne lisent jamais GitHub directement — chaque marque copie les fichiers sur son propre serveur et les sert à ses utilisateurs.

03 · Les garde-fous

Pourquoi un run cassé ne peut rien publier

Fail-closed, partout

Chaque étage calcule tout, vérifie tout, puis seulement écrit (écritures atomiques). Un fetch louche, une lane vide, une assertion ratée : le run passe rouge et l'état précédent continue d'être servi.

Deux sceaux de provenance

sanitized/provenance.json lie la curation aux miroirs exacts qui l'ont produite ; depuis le 2026-09-10, manifest.json porte aussi ce sceau — le catalogue refuse un dist/ qui ne vient pas de la génération courante de sanitized/.

Le plancher never-block

omit-from-blocklist ∪ default-blocklist-not-to-add : aucun vote, aucune liste publique, aucun append manuel ne peut faire bloquer ces domaines. Vérifié par assertion à chaque étage.

Budgets Chrome

≤ 30 000 règles, ≤ 5 000 redirect/modifyHeaders, ≤ 1 000 regex — assertés dans le code ET dans le YAML. Aujourd'hui : 10 287 / 56 / 56.

Change gate

Un mouvement de ±30 % des règles ou une chute de 20 % des domaines shippés retient la publication — un empoisonnement upstream ne part jamais en autopilote. Confirmation explicite requise.

Déterminisme + shadow-diff

Deux runs sur les mêmes entrées = octets identiques (aucun timestamp dans les artefacts). Le shadow-diff face au cache de production : 0 divergence inexpliquée.
